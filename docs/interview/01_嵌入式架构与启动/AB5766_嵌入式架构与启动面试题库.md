## 一、目录分层与软件架构

### Q1.1 你这个固件工程目录是怎么分层的？分层依据是什么？

**② 先说结论：**
分六层——`driver` 寄存器级外设、`bsp` 板级组合、`modules` 可复用协议和算法、`functions` 顶层运行模式、`os` 轻量调度、`libs` 预编译静态库。分层依据是「离硬件越近越底层、离产品功能越近越上层」，上层调下层，下层不反向依赖上层。

**③ 大白话解释：**
你可以把它想成「从零件到整车」。`driver` 是最底层的螺丝——直接读写寄存器，管 GPIO、时钟、ADC/DAC、定时器、UART 这些，它不关心产品是什么。`bsp` 是把零件组装成「板子能跑」的部件，比如系统启动、参数加载、按键、LED，它调 driver 但不知道产品是麦还是适配器。`modules` 是可复用的功能模块，无线收发、音频处理、编解码、音效、FOTA，这些是「换了产品也能用」的积木。`functions` 是最上层，决定「现在跑哪个模式」——麦发射还是适配器接收，把用户按键和消息映射到 modules。`os` 是非常薄的调度层，不是 RTOS，就是把消息派给回调。`libs` 是厂商给的预编译库，平台、蓝牙、编解码都在里面，我们靠 STRONG/WEAK 符号覆盖它。

**④ 项目证据：**
- 分层关系在聚合头文件 [header/include.h](../../header/include.h) 里能看到包含顺序：全局定义 → 生成配置（`xcfg.h`）→ 产品配置 → 公开 SDK API → BSP → 功能层 → 驱动层 → 模块层。
- `driver/` 提供寄存器级驱动；`bsp/bsp_sys.c` 里的 `bsp_sys_init()` 把这些驱动组合成板级行为。
- `functions/func.c` 管顶层模式选择；`modules/` 含 `wireless/`、`codec/`、`audio/`、`voice/`、`effect/` 等可复用单元。
- `libs/` 下是预编译的平台、C 运行时和蓝牙协议栈静态库。

**⑤ 设计取舍：**
好处是职责清晰、模块可复用、换产品配置时只动上层和配置。代价是层间有函数调用开销（虽然 -Os 下多数被内联）和「找调用链要跨多层」的认知成本。没有用更重的组件化框架，因为这是资源受限的 RISC-V 裸机，框架的开销不划算。

**⑥ 追问与回答：**
- 追问：modules 里的无线和音频算不算业务？为什么单独一层？
  - 答：算半业务。它「可复用」是关键——同一套 LC3S 编解码、同一套 PLC，麦和适配器都用。放 functions 里会和模式逻辑缠死，放 driver 又太抽象。modules 这层就是「跨产品可复用、但不碰具体硬件寄存器」的定位。

**⑦ 事实边界：**
目录分层是 E1（直接看目录结构），分层「设计意图」部分有解读成分，但和 CLAUDE.md 的架构描述一致。

**⑧ 面试收尾句：**
「所以这个分层你顺着 include 顺序从上往下看就是调用方向，这是后面所有题的基础，启动链、状态机都在这个分层里走。」

### Q1.2 为什么不用 RTOS？super-loop 加状态机够用吗？

**② 先说结论：**
够用，而且更合适。这个产品的并发性主要来自中断，不是多任务抢占；重活在连接后才跑、且由 5 毫秒 tick 和轻量 kick 驱动。super-loop 加功能状态机能把活儿派清楚，引入 RTOS 反而要管任务优先级和共享资源锁，对这种规模是过度设计。

**③ 大白话解释：**
RTOS 解决的核心问题是「多个任务同时抢 CPU、需要按优先级抢占调度」。但这个项目没有那种需求——它的「并发」是中断驱动的：SDADC 中断来了，清标志、kick 一下把活派出去，主循环里再处理。音频链路是流水线式的，采集→算法→编码→发送，一路串下来，不存在两个任务要同时跑还要互相抢资源。状态机管的是「现在该干什么模式」，不是「哪个任务该上 CPU」。所以一个不返回的 while 循环加一个状态变量，就够把流程跑顺。

**④ 项目证据：**
- `functions/func.c` 的 `func_run()` 是不返回的 while 循环，靠 `func_cb.sta` 分派到 `func_adapter()`/`func_mic_emit()`。
- `bsp/bsp_sys.c` 的 `usr_tmr5ms_thread_do()` 从 5 毫秒 tick 派生 10/50/100/500ms/1s 的周期工作——这是「软定时器」思路，不是 RTOS 任务。
- `bsp_sdadc.c` 的 `sdadc_isr_cb()` 只清标志 + kick，重活在 `sdadc_proc_cb()`——ISR 和工作回调解耦，不需要 RTOS 的延迟任务。

**⑤ 设计取舍：**
省了 RTOS 内核的 RAM/Flash 开销和上下文切换开销；代价是没有抢占，所以「重活不能在主循环里霸占太久」，必须靠中断 + kick 及时让出。这也是为什么音频链路里大量用「ISR 清标志、kick 派活、回调里做」的模式——保证主循环响应性。

**⑥ 追问与回答：**
- 追问：如果以后要加一个需要严格实时响应的任务（比如按键去抖必须在 1ms 内处理），怎么办？
  - 答：优先用中断 + 高优先级回调，而不是上 RTOS。按键本身可以走 AD 中断或定时器中断。只有当出现「多个互相独立、都有硬实时截止期、且不能用中断串行化」的任务时，RTOS 才真正必要，到那一步再评估。
- 追问：那 `kick` 是什么机制？
  - 答：是个轻量的「投递消息/触发回调」机制，本质是把「现在有活要干」这个信号从 ISR 或别处传到主循环侧的回调里去执行，避免在 ISR 里做重活。02 和 03 题库会展开讲。

**⑦ 事实边界：**
「不用 RTOS」是 E1（整个工程无 RTOS 内核、无任务调度源码）；「更合适」是工程判断，不是源码直接结论。

**⑧ 面试收尾句：**
「所以不是排斥 RTOS，是这套设备的并发模型就是中断驱动，super-loop 够了，RTOS 的开销不划算。这一点也决定了它的启动链和状态机设计。」

### Q1.3 讲一下这个工程的软件架构，从最高层到最底层。

**② 先说结论：**
最高层是 `functions` 的运行模式状态机，决定跑麦还是适配器；往下是 `modules` 的可复用协议和算法；再往下是 `bsp` 的板级组合和 `os` 的轻量调度；最底层是 `driver` 的寄存器级外设和 `libs` 的预编译平台库。架构的核心特征是「单镜像双角色 + 运行时切换」。

**③ 大白话解释：**
我从顶往下讲。最顶上 `functions/func.c` 是个不返回的主循环，根据角色进对应模式函数。模式函数（比如 `func_mic_emit`）是个状态机，管连接、扫描、退避这些流程，同时每轮调 `func_process()` 做公共周期活（喂狗、蓝牙主循环、充电、关机检测）和处理消息。再往下，模式函数调用 `modules` 里的无线收发、音频链、编解码、音效。`modules` 不直接碰寄存器，它用 `bsp` 暴露的接口和 `driver` 的外设。最底层 `libs` 是厂商预编译库，我们通过 `strong_symbol.c` 用 STRONG 符号覆盖它的 WEAK 函数来挂接自己的行为。这套架构最特别的地方是发射端和接收端共用一个镜像，运行时靠 `cfg_wireless_role` 切，内存层面两套角色代码在 Flash 各占一段 LMA、RAM 里同址复用一段 VMA、启动按角色搬运一份进 RAM。

**④ 项目证据：**
- 顶层分派：`functions/func.c` 的 `func_run()` 用 `wireless_role_is_adapter()` 决定 `func_cb.sta`。
- 角色宏：`libs/ble/api_wireless_mic.h` 里 `#define wireless_role_is_adapter() cfg_wireless_role`。
- 公共周期工作：`func.c` 的 `func_process()` 喂狗（`WDT_CLR`）、`bt_run_loop`、充电、关机检测。
- STRONG 覆盖：`projects/microphone/strong_symbol.c` 用 STRONG 函数覆盖库的 WEAK 符号。
- 内存分区：`projects/microphone/ram.ld` 定义 `.code_comm`/`.code_adapter`/`.code_emit`，`__emit_ram_vma = __adapter_ram_vma`（RAM 复用）。

**⑤ 设计取舍：**
单镜像双角色省一套代码维护和一次烧录管理（共用一个镜像入口和公共段），运行时靠 VMA 同址复用省一份 RAM，代价是两套角色代码的内存要精心分区、启动要搬运、链接脚本复杂度上升。注意 Flash 里两套各占一段 LMA（不省 Flash 空间），真正省的是 RAM 和维护成本。这个取舍在「双角色强相关、共享大量代码」的场景下是赚的。

**⑥ 追问与回答：**
- 追问：这套架构最大的耦合点在哪？
  - 答：无线时序和音频帧参数的耦合。采样率、帧大小、连接间隔、重传数、组合帧数是互相咬死的，动一个要推其他。02 和 03 会展开。

**⑦ 事实边界：**
架构描述是 E1；「VMA 同址复用省 RAM」是 E1/E2 推论（`ram.ld` 的 `__emit_ram_vma = __adapter_ram_vma` 段定义 + map 实占可证）；两套 LMA 各占 Flash 也由 `ram.ld` 的 `AT > flash` 和 map 的 `LOADADDR` 证。

**⑧ 面试收尾句：**
「这条链从顶层状态机一路到底层预编译库，每一层我都能指到具体文件，后面我按层展开讲。」

## 二、启动链与系统初始化

### Q2.1 从复位到进入主循环，完整的启动流程是怎样的？

**② 先说结论：**
`_start` → `main()` → 记录复位/唤醒原因、打印版本和内存诊断 → `bsp_sys_init()`（加载 `xcfg_cb`、设时钟、初始化外设、注册定时器回调）→ `func_run()`（按角色进模式状态机，不返回）。

**③ 大白话解释：**
复位之后先跑 C 启动代码（`_start`，由库提供），把 `.data` 搬好、`.bss` 清零，然后进 `main()`。`main()` 第一件事是记录复位原因——是上电、看门狗、还是唤醒，还会读唤醒源，这些信息后面调试和低功耗要用。然后打印版本号、SDK 版本、内存布局诊断（comm/heap/bss/bram 各段范围），这步对调试很重要，能一眼看出镜像布局对不对。接着调 `bsp_sys_init()` 做板级初始化，最后进 `func_run()` 这个不返回的循环。

**④ 项目证据：**
- `projects/microphone/main.c`：`sys_cb.rst_reason = sys_rst_init(...)`、打印 `Hello AB5766` 和 `SDK: v%04X LIBS: v%04X`、`sys_cb.wakeup_reason = lowpwr_get_wakeup_source()`、`code_info_dump()`、`bsp_sys_init()`、`func_run()`。
- `bsp/bsp_sys.c` 的 `code_info_dump()` 打印 comm/heap/bss/bram 范围。
- `projects/microphone/ram.ld` 的 `ENTRY(_start)`。

**⑤ 设计取舍：**
启动阶段就打印内存诊断，是为了在开发期快速发现段布局异常（比如 heap 被挤没了、某段没链进去）。生产里这些 printf 可以关，但保留成本低、收益高，所以一般留着。

**⑥ 追问与回答：**
- 追问：`_start` 你看得见吗？
  - 答：`_start` 是 C 运行时入口，在预编译的 C 库里，源码我看不到（预编译库边界），但 `ram.ld` 的 `ENTRY(_start)` 指定了它为入口，我能从 map 和反汇编看到它做了 `.data`/`.bss` 处理然后跳 `main`。
- 追问：复位原因怎么用？
  - 答：区分是上电冷启还是唤醒（比如从低功耗醒来）。唤醒要走 `bsp_periph_init()` 恢复外设，冷启则全量初始化。低功耗题（Q7.x）会展开。

**⑦ 事实边界：**
`main()` 内容是 E1；`_start` 内部是预编译库，只看到入口符号（E2）。

**⑧ 面试收尾句：**
「启动链看着简单，但它定了三件事：复位原因、内存布局、角色初始化，后面所有状态都建立在这上面。」

### Q2.2 `bsp_sys_init()` 具体做了哪些事？顺序为什么是这样？

**② 先说结论：**
`bsp_sys_init()` 依次做：加载运行时配置 `xcfg_cb`、初始化 PMU/无线状态/按键/LED/可选充电/ADC/USB、设置系统时钟、参数存储、注册定时器回调、可选 EQ/DRC 调试能力，最后置 `func_cb.sta = FUNC_BT`。顺序的原则是「先有配置再初始化外设、先有时钟再开需要时钟的外设」。

**③ 大白话解释：**
最关键是第一步 `xcfg_init(&xcfg_cb, sizeof(xcfg_cb))`——它把存在 Flash 参数区里的运行时配置加载到 `xcfg_cb` 这个全局结构体。后面所有外设的初始化都要读 `xcfg_cb` 里的字段，比如按键用哪个 IO、LED 怎么配、要不要充电功能，所以配置必须先加载。然后设系统时钟，当前配置是 24M。再注册 5 毫秒定时器回调，这是整个周期工作的心跳。最后把 `func_cb.sta` 设成 `FUNC_BT`，让 `func_run()` 知道接下来要进哪个模式。顺序不能乱——没加载配置就初始化外设，读到的全是默认值；没设时钟就开高速外设，可能跑不起来。

**④ 项目证据：**
- `bsp/bsp_sys.c` 的 `bsp_sys_init()`：`xcfg_init(&xcfg_cb, sizeof(xcfg_cb))`（约 line 202）→ 各外设初始化 → `sys_clk_set(SYS_CLK_SEL)`（约 line 241）→ `sys_set_tmr_enable(1,1)` → `func_cb.sta = FUNC_BT`（约 line 266）。
- `SYS_CLK_SEL = SYS_24M` 在 [config_ab5766_le_mic.h](../../projects/microphone/config_ab5766_le_mic.h) 定义。
- 定时器回调经 `strong_symbol.c` 的 `usr_tmr5ms_thread_callback()` 转到 `usr_tmr5ms_thread_do()`。

**⑤ 设计取舍：**
配置先于外设、时钟先于高速外设，这是嵌入式启动的通用原则。把 `func_cb.sta` 在 BSP 层就置好，是为了让 `func_run()` 的入口逻辑简单——BSP 负责把「该跑什么」也算清楚。

**⑥ 追问与回答：**
- 追问：`xcfg_cb` 和编译期配置宏什么关系？
  - 答：两层。编译期宏（`config_ab5766_le_mic.h` → `config_extra.h`）定「能力」——支持几路、采样率、帧大小；`xcfg_cb` 定「运行时取值」——当前角色、按键参数、音效等级。编译期能定的定死，运行时要切的留给 `xcfg_cb`。02 题库 Q2.1 展开。
- 追问：为什么初始时钟是 24M 不是更高？
  - 答：省功耗。24M 够启动和待机跑；真正要算力的是连上之后的解码和算法，那时候才 `sys_clk_req(INDEX_DECODE, SYS_160M)` 拉到 160M，断开再释放。Q7.1 展开。

**⑦ 事实边界：**
`bsp_sys_init()` 内容是 E1；具体行号以当前 `branch_02` 为准。

**⑧ 面试收尾句：**
「`bsp_sys_init` 的顺序本质就是『先配置后外设、先时钟后高速』，这是嵌入式启动的铁律，这个项目严格遵守。」

### Q2.3 运行时配置 `xcfg_cb` 是怎么加载的？和编译期配置怎么分工？

**② 先说结论：**
`xcfg_cb` 由 `xcfg_init()` 在 `bsp_sys_init()` 里从 Flash 参数区加载，存的是设备运行时取值（角色、按键、LED、音效等级等）。编译期宏（`config_ab5766_le_mic.h`/`config_extra.h`）定的是能力上限和默认值。两者分工：编译期能定死的定死，运行时需要切的留给 `xcfg_cb`。

**③ 大白话解释：**
你可以把它想成「出厂设置 vs 用户设置」。编译期宏像出厂设置——这颗芯片支持几路麦、采样率多少、帧大小多少，这些在烧录时就定死了，改要重新编译。`xcfg_cb` 像用户设置——当前这板子当麦还是适配器、按键双击时间、LED 亮什么、音效开几级，这些存在 Flash 一个叫参数区的地方，开机时 `xcfg_init()` 读出来填进 `xcfg_cb`，运行时还能改回 Flash。这样设计的好处是「同一份固件，配不同参数就能是不同产品」，不用为每个变体重新编译。

**④ 项目证据：**
- `bsp/bsp_sys.c`：`xcfg_init(&xcfg_cb, sizeof(xcfg_cb))`。
- 参数区布局：`config_ab5766_le_mic.h` 的 `CM_SIZE`、`CM_START`、`SYS_CM_PAGE`/`BLE_CM_PAGE`。
- 编译期宏链：`config.h` 选产品 → `config_ab5766_le_mic.h` 主配置 → `#include "config_extra.h"` 派生配置。
- 角色位 `cfg_wireless_role` 在 `modules/wireless/wireless.c` 定义，初始为 `true`（适配器），但实际运行时由 `xcfg_cb.wireless_adapter_en`/`wireless_mic_emit_en` 决定。

**⑤ 设计取舍：**
两层配置的好处是灵活性和确定性兼得——能力上限编译期定死保证不超限，运行时参数可调保证产品变体多。代价是两层要小心一致性，比如编译期关了某功能，运行时 `xcfg_cb` 里有对应字段也不能用，代码里靠 `#if` 守卫。

**⑥ 追问与回答：**
- 追问：参数区坏了怎么办？
  - 答：参数区有校验和冗余机制（`MAX_CM_PAGE` 定义最大页数），`xcfg_init()` 会校验。具体校验算法在预编译库边界内，我没深究；外部行为是「校验失败回退默认」。这是 E1/E3 之间的边界。
- 追问：能不能运行时改角色？
  - 答：角色位 `cfg_wireless_role` 是全局变量，理论上能改，但角色切换涉及代码搬运、外设重配、无线重连，不是改一个位那么简单。当前设计是开机时定角色，不在运行中切。02 题库 Q2.2 展开。

**⑦ 事实边界：**
`xcfg_init` 调用是 E1；`xcfg_init` 内部校验是预编译库，外部行为 E3 可测。

**⑧ 面试收尾句：**
「两层配置是这个项目做产品变体的基础，同一份固件配不同 `xcfg` 就是不同产品，这点在双角色设计里用到了极致。」

## 三、状态机与调度模型

### Q3.1 `func_run()` 是怎么决定跑哪个模式的？这个 while 循环的结构是什么？

**② 先说结论：**
`func_run()` 进来先用 `wireless_role_is_adapter()`（读 `cfg_wireless_role`）把 `func_cb.sta` 设成 `FUNC_ADAPTER` 或 `FUNC_MIC_EMIT`，然后进一个不返回的 while 循环：每轮调 `func_enter()` 切消息表，按 `func_cb.sta` switch 到对应模式函数，模式函数返回就进下一轮。

**③ 大白话解释：**
这是整个固件的「调度核心」。进来先判角色——如果是适配器，状态变量设成适配器模式；否则设成发射端模式。然后死循环：每轮先 `func_enter()`，这步会把当前模式对应的消息表挂上，这样按键消息能正确路由；然后 switch 看当前状态，是发射端就调 `func_mic_emit()`，是适配器就调 `func_adapter()`。模式函数自己内部也是个小 while，只有状态变量被改了（比如要关机、要切模式）才退出回大循环，再 switch 到新模式。所以是「大循环套小循环」，小循环管模式内部状态，大循环管模式切换。

**④ 项目证据：**
- `functions/func.c` 的 `func_run()`：`if (wireless_role_is_adapter()) func_cb.sta = FUNC_ADAPTER; else func_cb.sta = FUNC_MIC_EMIT;` 然后 `while(1){ func_enter(); switch(func_cb.sta){...} }`。
- `func_enter()` 里 `key_set_msg_tbl(func_info[func_cb.sta].msg_tbl)` 挂消息表。
- 模式函数 `func_mic_emit()`/`func_adapter()` 各自内部有 while 循环（见各自文件）。

**⑤ 设计取舍：**
「大循环套小循环」的好处是模式之间隔离清晰，切模式就是退出小循环回大循环；代价是模式切换不是即时的，要等当前模式函数自然退出到循环顶。这对这个产品没问题，因为模式切换（开关机、角色变）本身就不是高频实时事件。

**⑥ 追问与回答：**
- 追问：`func_cb.sta` 被谁改？
  - 答：模式函数内部、消息处理、低功耗逻辑都能改。比如关机消息会把 `func_cb.sta` 设成 `FUNC_PWROFF`，当前模式函数循环顶检测到就退出，大循环 switch 到关机流程。
- 追问：`FUNC_LE_DUT` 是什么？
  - 答：蓝牙 DUT 测试模式，由 `FUNC_LE_DUT_EN` 宏控制，当前配置是 0（关），所以这个分支不编译。打开后强制进测试模式。

**⑦ 事实边界：**
`func_run()` 结构是 E1。

**⑧ 面试收尾句：**
「这个大循环套小循环的结构是后面所有状态机的基础，麦和适配器的内部状态机都套在这个框架里。」

### Q3.2 公共周期工作 `func_process()` 做什么？为什么要单独抽出来？

**② 先说结论：**
`func_process()` 做所有模式都要做的公共活：喂看门狗、跑蓝牙主循环、处理充电、处理关机流程。抽出来是因为这些活和具体模式无关，每个模式的小循环每轮都要调一遍，集中放一处避免每个模式函数重复写。

**③ 大白话解释：**
不管你跑麦还是适配器，有些事每轮都得做——不喂狗会复位、蓝牙栈不跑主循环会卡、充电状态不轮询就停了。这些是「模式无关的公共活」。如果每个模式函数自己写一遍，既重复又容易漏。所以抽成 `func_process()`，每个模式的小循环每轮都调它。这样新增一个模式只要保证调了 `func_process()`，公共行为就有保证。

**④ 项目证据：**
- `functions/func.c` 的 `func_process()`：`WDT_CLR`、`bt_run_loop`、充电处理、`pwroff_process`。
- 各模式函数小循环里都调 `func_process()`（如 `func_adapter.c` 的 `func_adapter_process()` 末尾、`func_mic_emit.c` 同理）。

**⑤ 设计取舍：**
集中公共活是标准的状态机设计模式（公共动作 vs 模式特定动作）。代价是 `func_process()` 成了一个「什么都塞」的函数，要注意别让它变得太重阻塞模式循环。

**⑥ 追问与回答：**
- 追问：`func_process()` 里跑了重活会不会阻塞当前模式？
  - 答：会，所以 `func_process()` 里的活都要「短平快」。蓝牙主循环是栈提供的、设计成可分步的；充电轮询就是读个状态。真正重的活（解码、算法）不在这，在各自的回调里。
- 追问：喂狗为什么不能放中断里？
  - 答：放中断里喂狗就检测不到「主循环卡死」——中断可能正常但主循环死锁，狗还是被喂。放主循环里，主循环卡死就停喂，狗复位，这才是看门狗的意义。

**⑦ 事实边界：**
`func_process()` 内容是 E1。

**⑧ 面试收尾句：**
「`func_process` 这个设计就是『公共动作和模式动作分离』，是状态机的标准套路，保证喂狗和协议栈主循环在任何模式都不漏。」

### Q3.3 消息队列是怎么工作的？按键消息怎么路由到对应模式？

**② 先说结论：**
有个全局消息队列，中断和定时器把事件 `msg_enqueue` 进队，模式函数小循环每轮 `msg_dequeue` 取出处理。按键消息通过「消息表」路由——`func_enter()` 按当前模式挂对应的 `msg_tbl`，按键扫描出的原始键码经查表转成模式相关的功能消息。

**③ 大白话解释：**
消息队列是这套 super-loop 的「事件总线」。任何事件（按键、连接、USB 插拔、定时）都变成一个消息号塞进队列。模式函数每轮从队列取消息，有就处理、没有就 `MSG_NO`。按键路由的关键是「消息表」——同样的物理按键，在麦模式和适配器模式可能要做不同事。所以 `func_enter()` 切模式时，会把当前模式的消息表挂上，按键扫描出的键码经查表翻译成「这个模式下这个键该发什么功能消息」。这样物理键到功能消息的映射就和模式解耦了。

**④ 项目证据：**
- 模式函数小循环：`u16 msg = msg_dequeue(); if (msg != MSG_NO) func_xxx_message(msg);`（`func_adapter.c`、`func_mic_emit.c`）。
- 消息表挂载：`func.c` 的 `func_enter()` 调 `key_set_msg_tbl(func_info[func_cb.sta].msg_tbl)`。
- 消息处理示例：`func.c` 的 `func_message()` 处理 `MSG_PWR_HOLD`/`RELEASE`/`OFF`、`EVT_HCI_CMD`、`EVT_ONLINE_SET_EFFECT`。
- 入队示例：`func_adapter.c` 的 `usb_detect()` 里 `msg_enqueue(EVT_PC_INSERT)`/`EVT_PC_REMOVE`。

**⑤ 设计取舍：**
消息队列把「事件产生」和「事件处理」解耦——ISR 只管入队、主循环只管处理，符合 ISR 短原则。消息表让按键映射可配置、和模式解耦。代价是队列有上限，重负载下要防溢出。

**⑥ 追问与回答：**
- 追问：消息队列在中断和主循环之间共享，怎么保护？
  - 答：入队/出队操作本身是原子的或用临界区保护（预编译库提供），应用层不需要自己加锁。这是 E1 边界，具体实现在库内。
- 追问：消息丢了怎么办？
  - 答：关键消息（如关机）设计成幂等或可重发；周期事件（如 USB 检测）是状态轮询，丢一轮下轮还会产生，不会永久丢。这是「状态轮询 + 事件通知」混合的好处。

**⑦ 事实边界：**
消息入队/出队调用是 E1；队列原子性实现在预编译库。

**⑧ 面试收尾句：**
「消息队列加消息表是这套 super-loop 处理多源事件的标准方案，ISR 入队、主循环出队、消息表做模式相关路由。」

### Q3.4 5 毫秒 tick 是怎么派生出 10/50/100/500ms/1s 周期工作的？

**② 先说结论：**
有个 5 毫秒的硬件定时器中断，回调 `usr_tmr5ms_thread_do()` 里维护一个 `tmr5ms_cnt` 计数器，按计数对 2/10/20/100/200 取模派生出 10/50/100/500ms/1s 的周期工作。这是「软定时器」思路，用一个硬件定时器模拟多个软件定时器。

**③ 大白话解释：**
硬件定时器资源有限，不可能为「每 10 毫秒干一次」「每 50 毫秒干一次」各配一个定时器。所以只配一个 5 毫秒的，回调里数数——数到第偶数个就是 10 毫秒、数到 10 的倍数就是 50 毫秒、数到 20 的倍数就是 100 毫秒，以此类推。每个周期点干对应的活。这样 5 毫秒是「心跳」，所有更慢的周期都是心跳的整数倍派生出来的。这种设计在资源受限的裸机里很常见，省硬件定时器。

**④ 项目证据：**
- `bsp/bsp_sys.c` 的 `usr_tmr5ms_thread_do()`：从 `tmr5ms_cnt` 派生各周期（约 lines 60-97）。
- 回调挂接：`strong_symbol.c` 的 `usr_tmr5ms_thread_callback()` 转到 `usr_tmr5ms_thread_do()`。
- 定时器使能：`bsp_sys_init()` 里 `sys_set_tmr_enable(1,1)`。

**⑤ 设计取舍：**
一个硬件定时器派生多个软周期，省硬件资源、周期关系固定可推。代价是所有周期的「相位」都锁定在 5 毫秒的整数倍上，不能做任意非整数倍周期；而且 5 毫秒回调里活不能太重，否则影响所有派生周期的准时性。

**⑥ 追问与回答：**
- 追问：5 毫秒回调里能干重活吗？
  - 答：不能。它是中断上下文（或高优先级回调），重活会阻塞派生周期和主循环响应。重活要 kick 出去到主循环或专门回调里做。这正是音频链路用 ISR 清标志 + kick 模式的原因。
- 追问：为什么是 5 毫秒不是 1 毫秒？
  - 答：精度和开销的平衡。5 毫秒够覆盖人耳/人眼级别的周期（按键、LED、状态轮询），又不至于像 1 毫秒那样频繁进中断浪费 CPU。音频的实时性不是靠这个 tick，是靠 SDADC/DMA 中断。

**⑦ 事实边界：**
`usr_tmr5ms_thread_do()` 结构是 E1。

**⑧ 面试收尾句：**
「5 毫秒心跳派生所有慢周期，这是裸机里省硬件定时器的标准做法，重活都靠 kick 甩出去保证它不超时。」

## 四、ISR 与工作回调解耦

### Q4.1 为什么 SDADC 中断只清标志加 kick，重活放回调里？

**② 先说结论：**
中断里只做「判断全满/半满、清标志、kick 派活」三件轻量的事，重活（算法处理）放 `sdadc_proc_cb()` 回调里。这是「ISR 短原则」——中断里执行时间要尽量短，避免阻塞其他中断和主循环响应。

**③ 大白话解释：**
中断是「打断当前所有事」的机制，你在中断里待越久，其他中断和主循环就越久得不到响应。SDADC 每半缓冲（120 样点）来一次中断，如果在中断里直接做 EQ/DRC、LC3S 编码这些重活，可能要几百微秒，期间别的中断（比如蓝牙）就被卡住。所以中断只做最少的：看看是全满还是半满、清掉硬件标志、发个 kick 通知「有活要干」，然后立刻退出。真正重活由 kick 触发的回调在更合适的时机做。这样中断占用时间极短，系统响应性有保证。

**④ 项目证据：**
- `bsp_sdadc.c` 的 `sdadc_isr_cb()`：判断 `ALL_DONE`/`HALF_DONE`、清标志、`sdadc_done_proc_kick()`。
- `sdadc_proc_cb()`：`ALL_DONE`→`mic_enc_proc_cb(&sdadc_buf[RESELECT_SIZE], RESELECT_SIZE)`，`HALF_DONE`→`mic_enc_proc_cb(sdadc_buf, RESELECT_SIZE)`。
- 重活 `mic_enc_proc_cb()` 在 `modules/wireless/mic_proc.c`，做 Soft Gain/EQ-DRC/LC3S 编码。

**⑤ 设计取舍：**
ISR 短原则换来系统响应性，代价是「中断到处理」之间有延迟（kick 到回调执行不是立刻），对音频这种有缓冲的场景可接受。如果要求中断到处理零延迟，就要在 ISR 里做，但要承担阻塞风险。

**⑥ 追问与回答：**
- 追问：kick 到回调执行有多长延迟？
  - 答：取决于 kick 机制和当前 CPU 负载。这个项目用优先级事务 kick（`kick_dec_prio_trans`），延迟通常在微秒级，远小于一帧 2.5 毫秒的预算，所以不影响实时性。具体延迟我没测过精确值（E3 边界）。
- 追问：如果回调里又触发了新的中断需求呢？
  - 答：回调在主循环侧/可被中断抢占的上下文，新中断能正常打断回调。这正是把重活移出 ISR 的好处——回调里中断仍然响应。

**⑦ 事实边界：**
ISR 和回调结构是 E1；kick 延迟精确值是 E3，未测。

**⑧ 面试收尾句：**
「ISR 短原则是这个项目所有中断设计的共同特征，SDADC 是最典型的例子，清标志加 kick 三步走，重活全甩出去。」

---

### Q4.2 ISR 和工作回调之间共享的数据怎么保护？临界区怎么用？

**② 先说结论：**
共享数据用临界区保护——在访问共享变量的关键段前后 `GLOBAL_INT_DISABLE()`/`GLOBAL_INT_RESTORE()`，临时关中断保证原子性。比如无线发送放帧时，拷贝 TX 缓冲这段就包在关中断里。

**③ 大白话解释：**
ISR 和主循环侧的回调可能同时访问同一块数据，比如 TX 缓冲——ISR 可能更新发送状态、回调往里放帧。如果放帧拷到一半被 ISR 打断，数据就撕裂了。所以在「拷贝」这种必须原子的操作前后关中断，拷完再开。关中断时间要短，只包住真正不能被打断的几行，不能整个函数都关，否则又退化成 ISR 阻塞问题。

**④ 项目证据：**
- `modules/wireless/wireless_txrx_single.c` 的 `txpkt_put_frame()`：`GLOBAL_INT_DISABLE()` ... `memcpy` ... `GLOBAL_INT_RESTORE()`。
- rx/tx ping-pong buffer（`item[2]`、`rx_tog`/`rd_tog`）是共享结构。

**⑤ 设计取舍：**
临界区简单可靠，适合保护短小的临界段。代价是关中断期间影响响应性，所以只用在真正需要原子的操作上。对长临界段，临界区不合适，要用无锁设计或缓冲分离（如 ping-pong）。

**⑥ 追问与回答：**
- 追问：为什么用 ping-pong buffer？
  - 答：就是为了让生产者和消费者各操作一个缓冲、靠翻转切换，减少临界区范围。一边在用另一边，翻转那一下才需要保护，比全程锁一整块高效。
- 追问：`GLOBAL_INT_DISABLE` 是关所有中断吗？
  - 答：是关全局中断（通常操作状态寄存器或 CSR），关中断期间所有可屏蔽中断都不响应。所以必须极短。具体实现在预编译库/驱动层，E1 看到调用、内部 E2/E3。

**⑦ 事实边界：**
临界区调用是 E1；`GLOBAL_INT_DISABLE` 内部实现在驱动/库。

**⑧ 面试收尾句：**
「临界区只包短临界段、ping-pong 减少锁范围，这两招配合是这套中断密集系统保持响应性的关键，02 题库讲无线收发会再展开。」

## 五、STRONG/WEAK 符号覆盖与链接

### Q5.1 STRONG/WEAK 符号覆盖是什么机制？你项目里怎么用的？

**② 先说结论：**
预编译库里很多回调函数声明成 WEAK（弱符号），应用层可以定义同名 STRONG（强符号）函数，链接时强符号覆盖弱符号，库就调到你的实现。我们项目在 `strong_symbol.c` 里集中做这种覆盖，挂接自己的板级行为。

**③ 大白话解释：**
库想给你留扩展点，但又不能要求你非实现不可，所以把回调标成 WEAK——你不写，库用自己的默认实现（通常是空函数）；你写了同名的 STRONG 函数，链接器优先选你的，库就调你的。这比改库源码好，因为库是预编译的你也改不了。我们项目把所有这种覆盖集中在 `strong_symbol.c` 里，方便管理——比如 5 毫秒定时器回调、时钟切换回调、Flash 地址检查，都在这覆盖。

**④ 项目证据：**
- `projects/microphone/strong_symbol.c`：`cfg_sdk_version`（约 line 9）、`usr_tmr5ms_thread_callback()`（约 lines 54-58）→ 转到 `usr_tmr5ms_thread_do()`、`sys_clk_change_callback()`（约 lines 60-63）、`os_spiflash_addr_check()`（约 lines 33-51）、`pacc_effect_freq_shift_init` 空桩（约 lines 98-100，当 FREQ_SHIFT 关时）。
- WEAK 符号示例：`wireless.c` 的 `btstack_ble_reset_hash` 标 `WEAK`，提供默认实现。
- CLAUDE.md 明确：「需要有意挂接库行为时，应在 `strong_symbol.c` 处实现，而不是尝试修改预编译库。」

**⑤ 设计取舍：**
STRONG/WEAK 是不改库源码就能挂接库行为的标准手段，集中放 `strong_symbol.c` 便于审查。代价是要熟悉库暴露了哪些 WEAK 符号（靠头文件和 map 找），且同名符号要严格匹配签名，否则覆盖不生效还难发现。

**⑥ 追问与回答：**
- 追问：怎么确认覆盖生效了？
  - 答：E2 看 map——同名符号应该指向你的 `.o` 而不是库的 `.a`；E3 串口日志看你的实现有没有被调到（比如在回调里加 printf）。这是确认覆盖生效的标准两步。
- 追问：如果强符号签名写错了会怎样？
  - 答：变成定义了一个新符号，库的 WEAK 还在用，覆盖没生效，而且编译不报错（因为签名不同不算重定义）。这是隐蔽 bug，所以覆盖后一定走 E2 验证 map。

**⑦ 事实边界：**
`strong_symbol.c` 内容是 E1；覆盖生效验证靠 E2（map）+ E3（日志）。

**⑧ 面试收尾句：**
「STRONG 覆盖 WEAK 是不改预编译库就能挂接行为的唯一干净方式，但我们覆盖完一定走 map 加日志双重确认，因为签名写错不会报错只会静默失效。」

## 六、内存分区与段放置

### Q6.1 发射端和接收端共用镜像，内存上是怎么做到的？

**② 先说结论：**
两套角色代码在 Flash 里**各占一段 LMA**（加载地址，各存一份），但运行时在 RAM 里**复用同一段 VMA**（运行地址，`__emit_ram_vma = __adapter_ram_vma` 即同址复用）——同一块 RAM 同一时刻只跑一个角色。启动时按角色，只把当前角色那一套从 Flash 搬到这段 RAM。所以**省的是 RAM，不是 Flash**：Flash 里两套都在（各一段 LMA），RAM 里只占一份大小（VMA 复用）。

**③ 大白话解释：**
Flash 是非易失的，存代码；RAM 是易失的，跑代码。如果麦和适配器各占一份 RAM，即使同一时刻只跑一个角色，RAM 也被占满浪费。这里的巧思是：两套代码在 Flash 里是两段不同的位置（LMA 不同，各存一份），但运行时它们搬到**同一段 RAM**——`__emit_ram_vma = __adapter_ram_vma`，起始地址一样，意思是「这块 RAM 现在跑麦就装麦代码、跑适配器就装适配器代码」，互斥复用。启动时根据角色，把 Flash 里对应那套代码 memcpy 到这块 RAM。这样 RAM 只占一份大小（VMA 复用省 RAM），但 Flash 里两套各占一段（LMA 不同，Flash 不省）。能省一套代码维护和一次烧录管理，是因为共用一个镜像入口和公共段，不是因为 Flash 省了。

**④ 项目证据：**
- `projects/microphone/ram.ld`：`__base=0x10000000`、`__comm_ram_size`（LC3S 时 27k）、`__adapter_ram_vma = __comm_ram_vma + __comm_ram_size`、`__emit_ram_vma = __adapter_ram_vma`（RAM 复用）、`__mram_vma=0x18000`（32k，echo/reverb 复用）。
- SECTIONS：`.code_comm > comm AT > flash`、`.code_adapter > comm_adapter AT > flash`、`.code_emit > comm_emit AT > flash`（角色段互斥 RAM、各自 `AT > flash` 独立 LMA）。
- 搬运：`modules/wireless/wireless_proc.c` 的 `wireless_mic_load_code()` 用 memcpy 把代码从 LMA 拷到 VMA。

**⑤ 设计取舍：**
VMA 复用省 RAM（两套角色代码运行时同址复用，RAM 只占一份），但 Flash 里两套各占一段 LMA（不省 Flash）。代价是启动多一次搬运、两套代码不能同时跑（不能动态切角色，要重启）、链接脚本复杂。

**⑥ 追问与回答：**
- 追问：为什么 comm（公共）段不参与复用？
  - 答：comm 是两套角色都要用的公共代码（编解码、平台），两套都跑，必须独占 RAM 不复用。只有角色互斥的 `.code_adapter`/`.code_emit` 才复用。
- 追问：搬运会不会有 Flash 读取慢的问题？
  - 答：搬运是一次性的（启动或角色初始化时），量不大（几 KB），即使 Flash 读取有延迟也是一次性开销，可接受。运行时跑在 RAM 里是全速。

**⑦ 事实边界：**
段定义是 E1（`ram.ld`）；搬运是 E1（`wireless_mic_load_code`）；实际 RAM 占用 E2（map 可查）。

**⑧ 面试收尾句：**
「VMA 复用省 RAM 是单镜像双角色能落地的内存基础，链接脚本里 `__emit_ram_vma = __adapter_ram_vma` 的同址复用和 `AT > flash` 的 LMA 标注是关键。」

### Q6.2 `AT(...)` 段放置标注是什么意思？移动代码时要注意什么？

**② 先说结论：**
`AT(.xxx)` 是段放置标注，告诉链接器把函数放进指定的段（如 `AT(.com_text.sdadc.isr)` 放进 SDADC ISR 段）。这些段在 `ram.ld` 里被分配到特定 RAM/Flash 区域。移动时序或内存敏感代码时，必须保留 `AT(...)` 标注，否则代码可能被放到错误的内存区域。

**③ 大白话解释：**
默认情况下函数会被链接器放进默认段（`.text`），但有些代码必须放特定位置——比如 ISR 要放快速 RAM 里、启动代码要放特定段、两套角色代码要放各自的 `.code_adapter`/`.code_emit`。`AT(.段名)` 就是手动指定「这个函数放这个段」。你如果把一个 ISR 的 `AT(...)` 去掉，它可能被 GC 掉或放进默认 `.text`（可能在 Flash），中断响应就慢了。CLAUDE.md 也明确说要保留这些标注。

**④ 项目证据：**
- `bsp_sdadc.c`：`sdadc_isr_cb()` 标 `AT(.com_text.sdadc.isr)`。
- `wireless.c`：`printf_connect_message()` 标 `AT(.text.wireless.init)`、`wireless_channel_status()` 标 `AT(.text.adapter.proc)`。
- `func_adapter.c`：多个函数标 `AT(.text.func.adapter)`、`AT(.text.func.process.adapter)`、`AT(.usbdev.com.detect)`、`AT(.text.bsp.wireless_cb)`。
- CLAUDE.md：「移动时序或内存敏感代码时，保留这些标注。」

**⑤ 设计取舍：**
手动段放置给精确的内存控制，代价是开发者要懂段布局，标注错位会导致性能问题或运行错误，且 `--gc-sections` 可能把没被引用的段删掉，要靠引用或 `KEEP()` 保护。

**⑥ 追问与回答：**
- 追问：`--gc-sections` 会不会把 `AT` 段删掉？
  - 答：会，如果段里函数没人引用。`--gc-sections` 按引用关系删未用段。所以要么保证函数被引用、要么链接脚本里 `KEEP()` 保留。这是个常见坑——以为加了 `AT` 就在镜像里，实际被 GC 了。E2 看 map 确认。
- 追问：怎么知道某个段被分到哪块 RAM？
  - 答：看 `ram.ld` 的 SECTIONS，段名匹配到对应的 `> RAM区域 AT > flash`。map 也能看每个段的 VMA/LMA。

**⑦ 事实边界：**
`AT` 标注和段定义是 E1；GC 行为 E2（map 确认）。

**⑧ 面试收尾句：**
「`AT` 标注是这个项目精确控制内存放置的手段，移动代码必须带着标注走，还要防 `--gc-sections` 误删，这些都靠 map 验证。」

### Q6.3 VMA 和 LMA 有什么区别？这个项目怎么用？

**② 先说结论：**
VMA（Virtual Memory Address）是运行时地址，CPU 执行时用的；LMA（Load Memory Address）是加载地址，代码在 Flash 里实际存放的位置。这个项目代码从 Flash（LMA）搬到 RAM（VMA）运行，所以 VMA≠LMA，靠启动搬运和链接脚本 `AT` 语法协调。

**③ 大白话解释：**
代码在 Flash 里存着是一个地址（LMA），但跑起来 CPU 从 RAM 取指令是另一个地址（VMA）。如果代码必须跑在 RAM 里（比如速度要求），但 Flash 是非易失的存储介质，就得把代码从 Flash 的 LMA 拷到 RAM 的 VMA，拷完 CPU 按 VMA 执行。链接脚本用 `> RAM区域 AT > flash` 这种语法同时指定 VMA（RAM 区域）和 LMA（flash）。启动代码或角色搬运代码负责这个拷贝。如果 VMA 和 LMA 不一致但没搬运，CPU 取指取到的是 Flash 里没拷过来的旧数据，就跑飞了。

**④ 项目证据：**
- `ram.ld`：`.code_comm > comm AT > flash`——`> comm` 是 VMA（RAM），`AT > flash` 是 LMA。
- 搬运：`wireless_mic_load_code()` 把代码从 LMA memcpy 到 VMA。
- `code_info_dump()` 打印各段范围，启动时可核对 VMA/LMA 是否符合预期。

**⑤ 设计取舍：**
VMA/LMA 分离让代码能跑在 RAM（快）但存于 Flash（非易失），是嵌入式常见手法。代价是搬运开销和链接脚本复杂度，且必须保证搬运在代码被执行前完成。

**⑥ 追问与回答：**
- 追问：为什么不直接在 Flash 里执行（XIP）？
  - 答：可以 XIP，但 RAM 执行更快、功耗可能更低、且有些代码（如改写 Flash 时必须跑在 RAM）。这个项目部分代码 RAM 执行是为了速度和确定性。哪些 XIP 哪些 RAM 执行由段放置决定。
- 追问：怎么验证搬运对了？
  - 答：E2 看 map 确认段 VMA/LMA，E3 在搬运后跑个校验（如 CRC 或函数指针调用）确认 RAM 里代码正确。`code_info_dump()` 的输出也能帮助核对。

**⑦ 事实边界：**
VMA/LMA 定义是 E1；搬运和执行正确性 E3 验证。

**⑧ 面试收尾句：**
「VMA 是跑的地址、LMA 是存的地址，这个项目靠搬运连接两者，链接脚本的 AT 语法和 `code_info_dump` 是我核对这层关系的主要工具。」

## 七、中断、DMA、时钟、低功耗、看门狗取舍

### Q7.1 系统时钟为什么要从 24M 拉到 160M？怎么管理这个切换？

**② 先说结论：**
待机和启动用 24M 省功耗；连上之后解码和算法要算力，`sys_clk_req(INDEX_DECODE, SYS_160M)` 拉到 160M；断开 `sys_clk_free(INDEX_DECODE)` 释放回低频。时钟切换是「按需申请/释放」的引用计数式管理。

**③ 大白话解释：**
高频费电、低频省电但算不动。这个产品的算力需求是「连上才有」——没连的时候只需要跑跑状态机、轮询按键，24M 绰绰有余。连上之后要做 LC3S 解码、EQ/DRC、PLC 这些，24M 算不过来，必须拉到 160M。所以设计成「连接事件触发拉高、断开触发释放」。`sys_clk_req` 带 `INDEX_DECODE` 这种索引，说明是引用计数式——多个模块可以各自申请，都释放了才真正降频，避免一个模块降了影响另一个还在用。

**④ 项目证据：**
- 连接拉高：`wireless_proc.c` 的 `wireless_emit_notice()` 在 CONNECTED 事件里 `sys_clk_req(INDEX_DECODE, SYS_160M)`。
- 断开释放：DISCONNECT 事件里全断开时 `sys_clk_free(INDEX_DECODE)`。
- 初始时钟：`bsp_sys_init()` 里 `sys_clk_set(SYS_CLK_SEL)`，`SYS_CLK_SEL = SYS_24M`。
- 时钟切换回调：`strong_symbol.c` 的 `sys_clk_change_callback()`。

**⑤ 设计取舍：**
按需升降频省功耗，引用计数避免冲突。代价是状态机和时钟生命周期要同步——如果连上拉高了但状态机没正确处理，或者断开没释放，就会「该高速时低速卡顿」或「该低速时一直高速费电」。这是这个项目要重点测的时序点。

**⑥ 追问与回答：**
- 追问：切换时钟瞬间音频会不会断？
  - 答：切换有时延，期间音频链可能暂停或用缓冲兜底。具体兜底逻辑在音频回调里，我没逐行确认（E1 部分可见、E3 待测）。这是个好问题，是双板测试要重点看的。
- 追问：`INDEX_DECODE` 之外还有别的索引吗？
  - 答：应该有，比如编码、USB 可能各有索引，构成引用计数池。具体索引集在预编译库/头文件，我没全部列出（E1 部分、库内完整）。

**⑦ 事实边界：**
时钟申请/释放调用是 E1；切换瞬间音频行为 E3 待测；索引全集部分在库内。

**⑧ 面试收尾句：**
「时钟按需升降是功耗和算力的平衡，引用计数管冲突，但状态机和时钟同步是重点测的时序点，这块我标了待验证。」

### Q7.2 低功耗是怎么进的？睡眠和关机有什么区别？

**② 先说结论：**
有软关机（`func_pwroff`）和睡眠（sleep）两档。睡眠是「保留 RAM、停时钟、等唤醒源」的浅度低功耗，唤醒后恢复；软关机是更深的掉电（按 `PWROFF_MODE2` 配置，VDDIO 不掉电）。睡眠前会判断「能不能进」（只有特定消息允许进睡眠态），唤醒后要恢复时钟和重配外设。

**③ 大白话解释：**
睡眠像电脑待机——内存还在、CPU 停了、等个事件（按键、定时器、无线）唤醒继续跑，好处是唤醒快、状态不丢。关机像关机——更彻底掉电，重新上电要重新初始化。这个项目的睡眠比较克制：进睡眠前 `lowpwr_can_enter_sleep()` 会检查消息队列，只有像 1 秒心跳、500 毫秒这种「睡眠态允许的周期消息」在队里才进，有别的活就不睡。唤醒后 `sfunc_sleep_exit()` 恢复系统时钟、必要时 `bsp_periph_init()` 重配外设（因为睡眠可能停了外设时钟）。软关机 `func_pwroff()` 走 `PWROFF_MODE2`，VDDIO 不掉电是为了快速唤醒和保留部分状态。

**④ 项目证据：**
- `functions/func_lowpwr.c`：`lowpwr_can_enter_sleep()`（只允许 `MSG_SYS_1S`/`500MS` 等进睡眠）、`sfunc_sleep()`/`sfunc_sleep_exit()`（恢复 sysclk + `bsp_periph_init()`）、`sleep_process()`、`func_pwroff()`。
- `sys_sleep_cb()` 是 STRONG 覆盖。
- 关机模式：`config_ab5766_le_mic.h` 的 `SYS_PWROFF_MODE = PWROFF_MODE2`。
- 10 秒复位：`WK0_10S_RESET = 0`（当前关）。

**⑤ 设计取舍：**
睡眠浅、唤醒快但省电有限；关机深、省电多但唤醒要重初始化。两档配合覆盖「短时不用」和「长时间不用」。睡眠的克制检查（只允许特定消息进睡眠）是为了避免「有活没干就睡」导致响应延迟。

**⑥ 追问与回答：**
- 追问：睡眠中来了音频中断怎么办？
  - 答：音频中断是唤醒源之一，来了就唤醒。但当前如果没连接（没拉高速时钟），音频链不工作，所以睡眠通常发生在「断开、空闲」态。连着的时候一般不进深睡眠，因为有持续的无线和音频活动。
- 追问：唤醒后外设状态还在吗？
  - 答：不一定。如果睡眠停了外设时钟，相关外设寄存器可能失效，要 `bsp_periph_init()` 重配。`sfunc_sleep_exit()` 里就是判断「如果真睡了」就重配。这也是为什么唤醒逻辑要小心——重配不全外设就不工作。

**⑦ 事实边界：**
低功耗逻辑是 E1；唤醒后外设状态 E3 要实测。

**⑧ 面试收尾句：**
「睡眠和关机两档低功耗，睡眠浅唤醒快、关机深省电多，唤醒后外设重配是关键，这块的时序我也是双板重点测的。」

### Q7.3 看门狗怎么用？放在哪里喂？

**② 先说结论：**
看门狗在 `func_process()` 里每轮喂（`WDT_CLR`），因为 `func_process()` 是所有模式每轮都调的公共函数。这样不管跑哪个模式都喂狗，且主循环卡死会停喂触发复位——这才是看门狗的意义。

**③ 大白话解释：**
看门狗是个定时复位芯片的机制，你不喂它就复位。放对位置很关键：放中断里喂，主循环死锁了中断还在喂，狗永远不复位，失去意义；放主循环公共处喂，主循环卡死就停喂，狗复位，能自恢复。这个项目放 `func_process()` 里喂，因为它是模式无关的公共动作，每个模式每轮都调，保证「只要主循环在转就喂、卡死就停」。

**④ 项目证据：**
- `func.c` 的 `func_process()` 里有 `WDT_CLR`。
- 各模式小循环每轮调 `func_process()`。

**⑤ 设计取舍：**
放公共循环喂，覆盖所有模式、能检测主循环卡死。代价是不能检测「某个模式内部死循环但主循环还在转」——如果模式函数小循环里死循环不返回，`func_process()` 还是会被调（因为小循环里也调），狗还是被喂。这是个已知局限，要靠模式内部健壮性保证。

**⑥ 追问与回答：**
- 追问：那模式内部死循环怎么办？
  - 答：模式内部的关键循环要有超时退出机制（比如连接等待有 tick 超时）。看门狗兜底的是「主循环级别的卡死」，模式内逻辑死循环要靠设计避免，狗救不了。
- 追问：看门狗超时时间多长？
  - 答：由配置决定（`WDT` 相关宏/库内默认），我没记具体值（E0 在配置或库内、E3 可测复位时间）。

**⑦ 事实边界：**
喂狗位置是 E1；超时具体值部分在库内/配置。

**⑧ 面试收尾句：**
「喂狗放公共循环是看门狗正确用法——主循环卡死才停喂才复位，这个位置选对了狗才有意义。」

### Q7.4 DMA 双半缓冲相比单缓冲有什么好处？为什么用半满/全满两个中断？

**② 先说结论：**
双半缓冲是「一块缓冲分两半，DMA 采前一半时 CPU 处理后一半，反之亦然」，靠半满和全满两个中断切换。好处是采集和处理并行、延迟减半（不用等整块采满）、且缓冲连续不撕裂。

**③ 大白话解释：**
如果用单缓冲，DMA 要采满整块（240 样点）才中断一次，CPU 才能开始处理，期间 DMA 不能往同一块写（会撕裂），所以采集和处理是串行的，延迟是一整块的时间。双半缓冲把缓冲分两半：DMA 采前半（120 样点）时触发半满中断，CPU 处理前半，同时 DMA 接着采后半；后半满触发全满中断，CPU 处理后半，DMA 又回头采前半（已处理完）。这样采集和处理并行，延迟只有半个缓冲。对这个实时音频系统，半缓冲延迟减半很关键。

**④ 项目证据：**
- `bsp_sdadc.c`：`SDADC_DMA_SIZE = WIRELESS_MIC_SAMPLES_SELECT*2 = 240`（每半 120 样点）。
- `sdadc_isr_cb()` 判断 `HALF_DONE`/`ALL_DONE`。
- `sdadc_proc_cb()`：`HALF_DONE`→处理前半 `sdadc_buf`，`ALL_DONE`→处理后半 `&sdadc_buf[RESELECT_SIZE]`。

**⑤ 设计取舍：**
双半缓冲换来并行和低延迟，代价是中断频率翻倍（每半一次），但 ISR 极轻（清标志 + kick），开销可控。对音频这种「连续流、要低延迟」的场景，双半缓冲是标配。

**⑥ 追问与回答：**
- 追问：为什么不用更大的环形缓冲加定期取？
  - 答：环形缓冲延迟更大（要等攒够才取），且索引管理复杂。双半缓冲固定半缓冲切换，延迟确定（半个缓冲），适合实时音频。环形更适合非实时的大数据流。
- 追问：如果 CPU 处理慢于 DMA 采集会怎样？
  - 答：DMA 会覆盖还没处理的半缓冲，数据撕裂。所以处理时间预算必须小于半缓冲采集时间（120 样点 / 48k = 2.5ms）。这是音频链路时间预算的根本约束，03 题库展开。

**⑦ 事实边界：**
DMA 结构是 E1；时间预算 2.5ms 是 E0 推算（120/48k）。

**⑧ 面试收尾句：**
「双半缓冲是实时音频的标配，采集处理并行、延迟减半，但它定死了处理时间必须小于 2.5 毫秒半缓冲周期，这是整个音频链路时间预算的源头。」

## 八、架构类追问与场景题

### Q8.1 如果要加第三种角色（比如一个中继器），架构上要改什么？

**② 先说结论：**
要改三层：配置层加角色定义和 `wireless_role_is` 判断宏、`func.c` 的 `func_run()` switch 加新分支、链接脚本 `ram.ld` 加新角色的 VMA/LMA 段并处理三路 RAM 复用、新增 `func_relay.c` 模式函数。还要评估三角色 RAM 复用是否还放得下。

**③ 大白话解释：**
顺着现有双角色的设计走。第一，配置层定义新角色，仿照 `wireless_role_is_adapter` 加 `wireless_role_is_relay`，`cfg_wireless_role` 的取值域扩展。第二，`func_run()` 的 switch 加 `FUNC_RELAY` 分支调 `func_relay()`。第三，内存最难——现在两路 RAM 复用（`__emit_ram_vma = __adapter_ram_vma`），加第三路要么三路互斥复用同一块 RAM（要保证任两路代码之和不超过那块 RAM），要么重新分区。第四，写 `func_relay.c` 仿照现有模式函数结构。最后是 `modules` 里中继逻辑（收一路发一路）。

**④ 项目证据：**
- 角色判断：`wireless_role_is_adapter()` 宏（`api_wireless_mic.h`）。
- 分派：`func.c` 的 `func_run()` switch。
- 内存：`ram.ld` 的 `.code_adapter`/`.code_emit` 复用。
- 模式函数模板：`func_adapter.c`/`func_mic_emit.c` 结构可仿。

**⑤ 设计取舍：**
顺着现有模式扩展成本最低，但三路 RAM 复用要先算清是否放得下——如果三套代码都很大，复用一块 RAM 放不下，就要改成「两两互斥」或扩大 RAM，复杂度上升。这是评估新角色的关键卡点。

**⑥ 追问与回答：**
- 追问：运行时能不能动态切角色？
  - 答：当前不行（角色代码靠启动搬运，运行中切要重新搬运+重配外设+无线重连，等于软复位）。要支持得改成「三套代码都常驻 RAM」或「切角色走软复位」，前者费 RAM、后者有切换延迟。
- 追问：新角色的无线参数怎么配？
  - 答：编译期宏（链路数、帧大小）是全局的，如果中继要不同参数，要么单独编译变体，要么把部分参数移到运行时 `xcfg_cb`。这是配置层要决策的。

**⑦ 事实边界：**
现有结构是 E1；新角色改动是设计推断（未实现）。

**⑧ 面试收尾句：**
「加角色顺着现有模式走就行，但内存复用能不能放下是新角色的关键卡点，这是我评估扩展性的第一关注点。」

### Q8.2 状态机卡死（比如一直等连接不超时）怎么设计和排查？

**② 先说结论：**
设计上每个等待状态都有 tick 超时退出，不能「死等」。排查上靠串口日志看状态机停在哪个状态、tick 是否在走、超时条件是否触发，配合状态打印定位卡死点。

**③ 大白话解释：**
状态机最怕「死等一个永远不来的事件」。这个项目的连接等待都有超时——比如适配器 `ADAPTER_STA_INIT_W4_CONNECT` 状态用 `tick_check_expire(adapter.ticks, 2000)`，2 秒没等到就转 `START_ACTION`，不会死等。发射端连接失败有随机退避再重试。排查时，串口日志会打印状态转换（`func_adapter_process()` 里有 `TRACE` 打状态），看日志就知道停在哪个状态、tick 有没有在涨、超时算的对不对。如果 tick 不涨，可能是定时器没跑或被高优先级阻塞；如果 tick 涨但超时不触发，是超时逻辑 bug。

**④ 项目证据：**
- 适配器等待超时：`func_adapter.c` 的 `ADAPTER_STA_INIT_W4_CONNECT` 用 `tick_check_expire(adapter.ticks, 2000)`。
- 发射端退避：`func_mic_emit.c` 连接失败 `100+rand%500`、断开 `500+rand%500`、扫描后 `300+rand%300`。
- 状态打印：`func_adapter_process()` 的 `TRACE("adapter, state: %d\n", sta)`。

**⑤ 设计取舍：**
超时退出保证不卡死，随机退避避免多设备同时重连冲突。代价是状态机要正确管理 tick 和超时变量，漏了超时就会死等。

**⑥ 追问与回答：**
- 追问：随机退避的随机数哪来的？睡眠里能用吗？
  - 答：`rand` 是 C 库的伪随机，靠种子。种子来源要注意——如果用时间种子，但睡眠里时间可能不更新。这个项目用 `rand%N`，种子初始化要注意，具体我没深究（E1 部分）。这是个值得追问的点。
- 追问：状态打印生产里开着会不会影响性能？
  - 答：`TRACE` 由 `TRACE_EN` 宏控制，生产可关。开发期开着帮助调试，开销是几次 printf，对状态机这种低频事件可忽略。

**⑦ 事实边界：**
超时和退避逻辑是 E1；`rand` 种子细节部分在库。

**⑧ 面试收尾句：**
「状态机不卡死靠每个等待都有超时，排查靠串口日志看停在哪、tick 走没走，这套日志和超时是这个项目状态机能可靠运转的保障。」

### Q8.3 如果 RAM 不够了，你会从哪些地方省？

**② 先说结论：**
按代价从低到高：先关未用功能宏（让 `--gc-sections` 删掉对应代码）、减小算法缓冲和堆、检查 `AT` 段是否冗余、最后才考虑改算法或砍功能。每步都用 map 量化收益。

**③ 大白话解释：**
RAM 不够别急着砍功能。第一招最便宜——这个项目有大量 `WIRELESS_MIC_xxx_EN` 开关，关掉没用的（比如 ECHO、MAGIC、ROOM_REVERB 当前都关），对应的代码和数据缓冲会被 `--gc-sections` 删掉，立刻省 RAM/Flash。第二招，看 `OS_HEAP_SIZE`（当前 4K）和各算法缓冲能不能缩，但缩太小会算法溢出。第三招，看 `ram.ld` 段有没有冗余分配、`AT` 段有没有放错地方占了大块。第四招才是硬的——换更省内存的算法或砍功能。每改一步看 map 的 RAM 占用变化，用数据说话。

**④ 项目证据：**
- 功能开关：`config_ab5766_le_mic.h` 大量 `WIRELESS_MIC_xxx_EN`/`ADAPTER_xxx_EN`。
- GC：构建用 `-ffunction-sections` + `--gc-sections`。
- 堆：`config_extra.h` 的 `OS_HEAP_SIZE = 4*1024`。
- 段定义：`ram.ld` 的 `__comm_ram_size`、各 NOLOAD `.data_*` 段。

**⑤ 设计取舍：**
从便宜到贵逐步省，避免过早砍功能。代价是要熟悉每个开关和缓冲的量化影响，map 是核心工具。

**⑥ 追问与回答：**
- 追问：怎么知道关一个功能能省多少？
  - 答：改宏前后各出一次 map，对比 `__comm_ram_size` 或各段大小差值。这是最可靠的量化方法，比估算准。
- 追问：`--gc-sections` 会不会误删有用的？
  - 答：会，如果函数只被函数指针间接调用、链接器静态分析看不到引用，可能误删。靠 `KEEP()` 或保留引用保护。这是个经典坑，04 题库展开。

**⑦ 事实边界：**
省内存手段是 E1/E2；量化靠 map 对比。

**⑧ 面试收尾句：**
「省 RAM 从关开关到砍功能逐级来，每步看 map 量化，这是资源受限项目做内存优化的方法论，map 是核心工具。」

## 九、汇总与边界声明

### Q9.1 这套架构最核心的设计决策是哪几个？你怎么评价它们的取舍？

**② 先说结论：**
三个核心决策：单镜像双角色（VMA 同址复用省 RAM + 省一套代码维护，代价是链接脚本和搬运复杂）、裸机 super-loop + 状态机 + 消息队列（够用且省内核开销，代价是无抢占）、ISR 短 + kick 解耦 + 双半缓冲（保证响应性和实时性，代价是时间预算卡死）。三者互相支撑，契合「资源受限的实时音频设备」定位。

**③ 大白话解释：**
第一，单镜像双角色是这个项目最鲜明的决策——共用一个镜像、靠运行时配置切角色，运行时 VMA 同址复用省一份 RAM，适合双角色强相关的产品，但链接脚本和启动搬运要精心设计（Flash 里两套各占一段 LMA，不省 Flash 空间）。第二，不上 RTOS 用 super-loop，因为并发是中断驱动不是任务抢占，省内核开销，但要求重活不能霸占主循环，所以配套了 ISR 短 + kick 这套机制。第三，音频链路用双半缓冲 + ISR 清标志 kick，换来采集处理并行和低延迟，但卡死了处理时间必须小于半缓冲周期。三个决策互相咬合——双角色同址复用省内存让 super-loop 可行，super-loop 的无抢占靠 ISR 短 + kick 保证响应，双半缓冲的实时性靠 ISR 短实现。

**④ 项目证据：**
综合前述各题证据：`ram.ld` 双角色段、`func.c` super-loop、`bsp_sdadc.c` 双半缓冲 + kick。

**⑤ 设计取舍：**
整体是为「低成本 RISC-V 芯片 + 实时无线音频 + 双角色产品」量身定制的，没有过度设计，也没有在关键处偷工。评价是「恰当」而非「豪华」。

**⑥ 追问与回答：**
- 追问：如果芯片升级了、RAM 大了，这套架构还合适吗？
  - 答：核心仍合适，但可能解锁更多功能（更多音效、更高采样率）。RAM 大了之后 RTOS 的吸引力会上升（如果并发需求增加），但不增加并发就不必上。架构要随需求演进，不是越大越好。

**⑦ 事实边界：**
设计评价含主观判断，但基于 E1 架构事实。

**⑧ 面试收尾句：**
「这三个决策互相咬合、贴合产品定位，是我评价这套架构『恰当』的依据，也是我能在面试里讲清楚整条链路的基础。」

### Q9.2 哪些架构点你还没完全验证，需要诚实标注边界？

**② 先说结论：**
主要是预编译库内部（启动 `_start`、`xcfg_init` 校验、消息队列原子性、时钟索引全集、`GLOBAL_INT_DISABLE` 实现、LC3S/PLC/PACC/BLE 内核），这些我只看到接口和外部行为，没看源码；以及一些运行时时序（时钟切换瞬间音频、唤醒后外设状态、kick 延迟精确值），需要双板实测。

**③ 大白话解释：**
我诚实标三类边界。第一类是预编译库内部——`_start` 干了什么、`xcfg_init` 怎么校验、消息队列怎么保证原子、时钟引用计数有哪些索引、`GLOBAL_INT_DISABLE` 怎么实现、还有 LC3S/PLC/PACC/BLE 的内部算法，这些源码在库里我看不到，只能说接口和外部行为，不编内部。第二类是运行时时序——时钟切换那一瞬间音频会不会断、睡眠唤醒后外设状态全不全、kick 到回调的精确延迟，这些要双板和示波器实测，我没有完整 E3 数据。第三类是前面提到的 RETRY×LINK×FRAME=150 和注释「72byte」的矛盾，要协议侧/双板验证。

**④ 项目证据：**
