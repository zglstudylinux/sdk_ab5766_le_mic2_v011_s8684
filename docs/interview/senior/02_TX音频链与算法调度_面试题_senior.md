## 1. 概念理解题

### 题目 2.1 TX 帧处理的实时预算计算（★★★★ / 概念理解）

**题目**：已知无线周期为 4×1.25ms=5ms，一帧 2.5ms=120 samples@48kHz。请估算 TX 每帧“从 SDADC 数据就绪到 LC3S 编码完成”的可用时间预算，并说明 `WIRELESS_MIC_EQ_DRC_DELAY=200` 的含义。

**考察点**：
- 主考点：帧级时序预算；
- 副考点：算法耗时宏定义的意义；
- 区分点：能否区分“帧周期 2.5ms”与“无线周期 5ms”以及双缓冲。

**参考答案**：
帧周期 2.5ms 是音频采集/处理周期；无线周期 5ms 是空中传输周期，两者通过 DMA 双缓冲对齐。每帧处理预算理论上是 2.5ms，但实际需扣除无线调度、编码耗时（`WIRELESS_MIC_ENC_MAX_US`）、以及可能的 double buffering 保护。`WIRELESS_MIC_EQ_DRC_DELAY=200`（[config:100](projects/microphone/config_ab5766_le_mic.h#L100)）表示为 EQ/DRC 预留 200 单位（通常是 μs 或计数器单位）的处理时间，用于系统调度时计算是否超时。

**评估标准**：
- ⭐⭐⭐ 能区分 2.5ms 与 5ms 并解释 `EQ_DRC_DELAY`；
- ⭐⭐ 能说出 2.5ms；
- ⭐ 混淆周期。

### 题目 2.2 AINS4_32K 与 EQ_DRC 的调度模型混搭（★★★★ / 概念理解）

**题目**：AINS4_32K 在 `thread_alg` 线程跑，EQ_DRC 在 `mic_enc_proc_cb` 同步跑。如果两者顺序颠倒（先 EQ_DRC 后 AINS4），从算法效果与实时性看有何风险？

**考察点**：
- 主考点：算法顺序对音质与实时性的影响；
- 副考点：同步/异步耦合；
- 区分点：能否指出异步算法的“攒帧”特性会导致同步 EQ 输出延迟。

**参考答案**：
当前顺序是 AINS4 → SRC → EQ_DRC。若改先 EQ_DRC 后 AINS4：
1. **算法效果**：AINS4 处理的是未经过 EQ/DRC 的原始信号，可能因动态范围过大导致降噪效果变差；
2. **实时性**：AINS4 是异步攒帧（需 240 点触发一次），会额外引入 2.5~5ms 延迟；而 EQ_DRC 是同步原位处理。若 EQ_DRC 在 AINS4 前运行，其输出需等待 AINS4 攒帧完成，导致后续 SRC/编码被 delay，可能错过无线发送窗口。

**评估标准**：
- ⭐⭐⭐ 能同时从音质与实时性分析；
- ⭐⭐ 能分析一方面；
- ⭐ 完全不知道。

### 题目 2.3 `mic_enc_proc_cb` 的“条件编译”与“运行时分支”混用（★★★★ / 源码追踪）

**题目**：`mic_enc_proc_cb()` 中大量 `#if` 宏控制，同时又有 `if (mute_flag)`、`if (sys_cb.mic_alg_en)` 运行时判断。请解释这两者的编译/运行边界，并指出哪一层先检查。

**考察点**：
- 主考点：编译期裁剪 vs 运行时开关；

`mic_enc_proc_cb()` 首先执行 mute 检查（第 280-293 行），然后才走到 `if(sys_cb.mic_alg_en)`（第 295 行）。编译期宏决定了 `mic_alg_en` 为 1 时具体会执行哪些算法调用。

### 题目 2.4 AINS4_32K 的“两级延迟”推导（★★★★★ / 源码追踪）

**题目**：请精确计算 AINS4_32K 引入的端到端算法延迟。提示：`FRAME_LEN=240`，`PROCESS_OUT_SAMPLES=80`，输入 48kHz。

**考察点**：
- 主考点：异步算法的延迟计算；
- 副考点：乒乓缓冲与攒帧；
- 区分点：能否算出“2.5ms 收集 + 5ms 处理”或类似结果。

**参考答案**：
AINS4_32K 使用乒乓缓冲，每缓冲 240 点：
- 攒满一帧需 240/48=5ms；
- 但输出按 `PROCESS_OUT_SAMPLES=80` 分块，每 80 点=1.67ms 输出一次；
- 输入是流式的（每 120 点=2.5ms 进来一次），通过 `memcpy` 分别写入两个缓冲；
- 实际算法延迟 ≈ 5ms（攒满）+ 处理时间（若 1ms 内完成，则总计约 6ms）。

**评估标准**：
- ⭐⭐⭐ 能算出 5ms 攒帧 + 处理时间；
- ⭐⭐ 能算出攒帧时间；
- ⭐ 完全不知道。

## 3. 调试排查题

### 题目 2.5 EQ_DRC 开启后爆音（★★★★★ / 调试排查）

**题目**：开启 `WIRELESS_MIC_EQ_DRC_EN=1` 后，RX 听到周期性爆音。请从 `loc_mic_pacc_process()` 的输入格式、`soft_gain` 扩展、`pacc_ctl_proc` 时序三个角度分析。

**考察点**：
- 主考点：PACC 数据格式与同步；
- 副考点：Soft Gain 与 PACC 数据位宽匹配；
- 区分点：能否指出 S16 与 S32 混用导致溢出或截断。

**参考答案**：
1. **输入格式**：`loc_mic_pacc_enable()` 设置 `S32_Q15` 输入（若开 Soft Gain），若实际传入 S16，PACC 会按 S32 解释导致音量爆炸；
2. **Soft Gain 扩展**：`soft_gain_proc_16bit` 返回 s32，若直接赋给 s16 会截断高位，产生爆音；
3. **时序**：`pacc_ctl_proc()` 若未在前一次完成前被再次 kick，会导致 CS 链表状态错乱，输出噪声。

**评估标准**：
- ⭐⭐⭐ 能三角度分析并给出修复建议；
- ⭐⭐ 两角度；
- ⭐ 一角度。

## 4. 设计权衡题

### 题目 2.6 软件 SRC vs 硬件 SRC（★★★★ / 设计权衡）

**题目**：当前 `src_frame_resample()` 由软件实现（`modules/voice/src.c` 或库函数）。若芯片提供硬件 SRC，你会替换吗？为什么？

**考察点**：
- 主考点：软硬件加速选型；
- 副考点：PACC 复用、功耗、精度；
- 区分点：能否比较算力占用与音质。

**参考答案**：
若硬件 SRC 精度足够（如 24bit）且不占用 PACC，应替换；因为：
- **算力**：软件 SRC 占用 CPU，在 160M 下 120 点×插值运算耗时可观；
- **功耗**：硬件 SRC 更省电；
- **音质**：软件 SRC 若用简单线性插值，音质不如硬件 polyphase；需权衡 `pcm_48k` 缓冲区大小与 `src_frame_resample` 返回值。

**评估标准**：
- ⭐⭐⭐ 能三角度分析；
- ⭐⭐ 两角度；
- ⭐ 一角度。
